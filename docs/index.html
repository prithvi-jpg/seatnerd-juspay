Why this industry

Live ticketing is where an orchestrator earns its keep

Surge is the failover story

A ticket drop concentrates demand into minutes. A PSP that browning-out for 90 seconds costs the entire event's revenue — not one order. Routing around a failing processor is the difference between a sold-out show and a support storm.

Auth-then-capture is structural

A ticket doesn't exist until a barcode is issued. Money must be held, not taken, while inventory is held. The payment lifecycle has to be welded to the fulfilment lifecycle — the core of this build.

Mobile, wallet-first

US ticketing converts on phones. Apple Pay / Google Pay are the primary lever, not a nice-to-have — one SDK renders them all via Hyperswitch.

Marketplace + regulatory shape

Venue / promoter / platform splits; high fraud (selective 3DS); and the FTC all-in-pricing rule (2025) that names live-event ticketing — the total must be shown up front. Fees are computed at hold time and never added later.

The flows it needs

  • Seat hold → authorize → issue barcode → capture
  • Connector failover on transient processor failure
  • Hard declines stop the cascade — no wasted attempts
  • Hold expiry → void → inventory release (cron)
  • Webhook reconciliation, idempotent
  • Split payments · 3DS decision rules · network tokens · disputes
Decisions & reasoning

Four choices, each driven by the vertical

1 · Manual capture

capture_method: "manual" — authorize at hold, capture strictly after barcode issue, void on expiry. Charged-for-a-ticket-that-never-existed becomes impossible. Verified against IntentStatus::RequiresCapture and CaptureMethod::Manual in crates/common_enums/src/enums.rs.

2 · Web SDK + server-side mutations

UnifiedCheckout driven by client_secret. The browser holds only the publishable key; the snd_ key never leaves the server. PCI SAQ-A posture; wallets/BNPL render from the SDK.

3 · Purpose-built engine, not a fork

Medusa/Saleor/Pretix evaluated and rejected: each costs a non-Vercel backend + Postgres + Redis + a plugin system to learn — a third of a 24h budget before payment code. The interesting engineering here is the payment↔inventory coupling and routing under surge: built small, explicit, and fully owned.

4 · GSM-style retry policy

Verified live: transient connector error and stolen card return the same DC_08 / UE_9000. Only the message differs. Retry decisions key on (connector, code, message) — retry the retryable, never a stolen card.

Hard decline — the cascade stops

4 · Connector limitation, handled defensively

Sandbox dummy connectors ignore capture_method: manual and settle immediately. A follow-up /capture returns:

IR_14: expected state is requires_capture, partially_captured_and_capturable, processing

The app reads the actual returned status and branches (alreadyCaptured) instead of assuming the ideal path. The design keeps manual capture — it is correct for ticketing — and survives the sandbox's shortcuts. That the IR_14 error text itself enumerates the valid capture states is the router's state machine speaking at runtime, matching IntentStatus in source.

What we didn't build, and how we would

Scoped out on purpose, mapped on purpose

Split payments & payouts

Venue / promoter / platform splits. SplitPaymentsRequest exists in the API (stripe_split_payment, adyen_split_payment). Approach: single auth, split at capture; promoter settlement via the Payouts API with per-entity ledger rows in order_events.

3DS decision manager

Ticketing fraud is high but blanket SCA hurts conversion. ThreeDsDecisionRule routing kind (verified in api_models/src/routing.rs): rules keyed on amount tier + risk signal — challenge only where fraud economics justify it.

Network tokenization

Dedicated token webhook path exists (network_tokenization_incoming). Approach: tokenize at save-card time, route token-present attempts preferentially — lifts auth rates, which is the panel's own headline topic.

Apple Pay

Requires merchant identity certificate + domain verification — a real-account blocker in the sandbox. Called out rather than faked: the SDK already renders Apple Pay; enabling it is dashboard + cert work.

Disputes

Webhook-driven intake, evidence workflow, scheme-specific timelines. High-value in ticketing (card-not-present fraud at scale).

Virtual waiting room

Queue-It style gate in front of the onsale to flatten surge — the demand-side complement to the supply-side failover story.
